# incident-triage

Sentry가 올린 에러 하나를 보고 **사람을 부를 일인지** 판정합니다.

봇은 이 판정이 `true`일 때만 다음 단계(소스를 읽는 분석)로 넘어갑니다. 그래서 이 스킬은 값싼 문지기입니다 — 여기서 거른 건은 채널에 아예 올라가지 않습니다.

## 소스를 읽지 마세요

이 스킬은 **빈 디렉터리에서 실행됩니다.** 저장소가 없으니 파일을 찾지 마세요. 주어진 이슈 메타와 대표 이벤트 JSON만으로 판정합니다.

원인을 밝히는 것은 이 단계의 일이 아닙니다. 원인은 다음 단계(`incident-analyze`)가 소스를 읽고 합니다. 여기서는 **"넘길 가치가 있는가"**만 봅니다.

## 판정 기준

`action_needed`를 `true`로 두는 것:

- 서버 오류(5xx)나 처리되지 않은 예외 — 특히 요청 경로에서 터진 것
- 데이터가 잘못 저장되거나 유실될 수 있는 실패
- 인증·결제·외부 연동처럼 사용자가 막히는 지점
- 짧은 시간에 반복 중이거나(`발생 횟수`가 큼), 고쳤다고 본 것이 다시 터진 것(`상태: regressed`)

`false`로 두는 것:

- 잘못된 요청에 대한 정상적인 거절 (4xx 검증 실패, 잘못된 파라미터)
- 크롤러·스캐너·헬스체크가 유발한 잡음
- 로컬·테스트 환경에서만 나는 것
- 이미 의도적으로 던지고 있는 예외 — 흐름 제어용으로 보이는 것

**애매하면 `true`입니다.** 놓치는 쪽이 시끄러운 쪽보다 나쁩니다. 사람은 채널에서 '무시' 버튼을 누를 수 있지만, 올라오지 않은 건은 아무도 모릅니다.

## severity

| 값 | 언제 |
|---|---|
| `high` | 사용자가 지금 못 쓰고 있음. 데이터 손상·유실 가능성 |
| `medium` | 일부 기능이나 일부 사용자만 영향. 우회로가 있음 |
| `low` | 동작에 영향은 적지만 남겨둘 이유가 있음 |

`action_needed`가 `false`면 `low`로 둡니다.

## 출력 형식

**JSON 객체 하나만** 출력합니다. 설명·인사말·코드 펜스를 앞뒤에 붙이지 않습니다.

```json
{
  "action_needed": true,
  "reason": "결제 승인 요청에서 NPE로 5xx가 반복 중",
  "severity": "high"
}
```

| 필드 | 설명 |
|---|---|
| `action_needed` | **필수.** boolean이 아니면 봇이 `true`로 간주합니다 |
| `reason` | 판정 근거 한 줄. 봇 로그에만 남고 채널에는 안 나갑니다 |
| `severity` | `high` \| `medium` \| `low` |

형식이 깨지면 봇은 **`action_needed: true`로 보고 분석으로 넘깁니다.** 답변 스킬과 반대 방향입니다 — 형식 하나 때문에 진짜 장애를 못 보고 지나가는 것이 헛걸음보다 나쁘기 때문입니다. 그래도 형식을 지키세요. 폴백이 잦으면 이 단계가 있으나 마나입니다.

## 입력 형태

```
Sentry 이슈 ID: 4501
짧은 ID: TMT-BE-7
제목: NullPointerException
발생 위치: PaymentService.approve
레벨: error
상태: new
발생 횟수: 37
최초 발생: 2026-09-05T03:00:00Z
최근 발생: 2026-09-05T03:41:00Z
Sentry 링크: https://sentry.io/issues/4501/

대표 이벤트(JSON):
{ ... }
```

`상태`는 Sentry의 substatus입니다 — `new`(새로 생김) 또는 `regressed`(해결된 줄 알았는데 재발). 계속 나던 에러는 봇이 여기까지 보내지 않습니다.
