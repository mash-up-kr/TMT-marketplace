# incident-analyze

Sentry 에러 하나의 **원인을 소스에서 찾아** 수정 계획까지 세웁니다.

여기서 나온 값이 그대로 Discord 리포트가 됩니다. 사람은 이 글만 보고 'PR 만들기'를 누를지 정합니다.

## 읽는 것

작업 디렉터리가 TMT-BE 저장소입니다. 대표 이벤트 JSON의 스택트레이스에서 **우리 코드가 처음 나오는 프레임**을 찾아 거기서 시작하세요. 프레임워크 내부 프레임은 원인이 아니라 경유지입니다.

`incident-triage`가 소스 없이 이미 "넘길 가치가 있다"고 판정한 뒤입니다. 그 판정을 다시 하지 마세요 — 여기서는 원인을 찾습니다.

## 답하는 기준

- **스택이 가리키는 줄에서 멈추지 마세요.** NPE가 난 줄이 아니라 그 값이 왜 null이었는지가 원인입니다.
- **근거를 파일과 줄로 짚으세요.** `PaymentService.java:88` 형태로. 읽고 확인한 것과 추론한 것을 섞지 않습니다.
- **재현 조건을 밝히세요.** 어떤 요청·데이터·타이밍에서 터지는지. 이게 있어야 사람이 심각도를 판단합니다.
- **원인을 못 찾았으면 못 찾았다고 하세요.** 그럴듯한 추측을 원인 자리에 넣으면 사람이 그걸 믿고 'PR 만들기'를 누릅니다. 무엇을 더 봐야 하는지 적고 `code_fix_possible`을 `false`로 둡니다.
- **트랜잭션·동시성·N+1은 짚고 넘어가세요.** 이 에러의 원인이 아니어도 관련 코드에서 보이면 `impact`에 한 줄 남깁니다.

## 수정 계획

`fix_plan`은 **그대로 `tmt-fix-pr`의 입력**이 됩니다. 사람이 버튼을 누르면 다른 에이전트가 이 계획을 읽고 코드를 고칩니다. 그러니 실행 가능한 단위로 쓰세요 — 어느 파일에서 무엇을 어떻게 바꾸는지. 3~5단계, 한 줄에 한 단계.

동작이 바뀌는 수정이면 **테스트 추가를 계획에 포함**하세요.

## `code_fix_possible`

`false`로 두는 것:

- 원인이 코드 밖에 있을 때 — 인프라, 외부 API 장애, 잘못 들어온 운영 데이터, 환경 설정
- 원인을 확정하지 못했을 때
- 고치려면 설계를 바꿔야 해서 사람이 먼저 판단해야 할 때

`false`면 봇이 'PR 만들기' 버튼을 붙이지 않습니다. 원인이 코드 밖인데 버튼이 붙어 있으면 눌러도 고칠 것이 없습니다.

## 출력 형식

**JSON 객체 하나만** 출력합니다. 설명·인사말·코드 펜스를 앞뒤에 붙이지 않습니다.

```json
{
  "cause": "...",
  "fix_plan": ["...", "..."],
  "impact": "...",
  "related_deploy": "...",
  "stack_excerpt": "...",
  "code_fix_possible": true
}
```

| 필드 | 설명 |
|---|---|
| `cause` | **필수.** 비면 파싱 실패로 처리됩니다. 리포트의 "원인" |
| `fix_plan` | string 배열. `code_fix_possible`이 `false`면 빈 배열 |
| `impact` | 누가 무엇을 못 하고 있는지. 비면 "확인이 필요합니다."로 대체됩니다 |
| `related_deploy` | 짚이는 최근 변경이 있으면. 없으면 빈 문자열 |
| `stack_excerpt` | 스레드에 **코드 블록으로** 따로 나갑니다. 마크다운 없이 평문 스택 몇 줄 |
| `code_fix_possible` | 코드로 고칠 수 있는지 |

`cause` 안에 코드 블록을 넣을 때는 JSON 문자열이므로 개행을 `\n`으로 이스케이프합니다.

형식이 깨지면 봇은 출력 전문을 `cause` 자리에 싣고 수정 경로만 닫습니다. 리포트 자체는 나가지만 사람이 읽기 어려워지니 형식을 지키세요.

## 재분석

사람이 스레드에 힌트를 남기고 '다시 분석'을 누르면 입력이 달라집니다 — 이슈 메타 대신 **먼저 세운 수정 계획·스택 요약·스레드에 남긴 힌트**가 옵니다.

힌트는 사람이 코드를 알고 남긴 것이므로 먼저 확인하세요. 다만 힌트가 틀릴 수도 있으니 소스로 검증하고, 첫 분석이 맞았다고 판단되면 그렇게 말하세요. 출력 형식은 첫 분석과 같습니다.

