# tmt-fix-pr

승인된 수정 계획대로 **TMT-BE 저장소의 작업 트리를 고칩니다.**

## 하지 않는 것

브랜치 생성·커밋·푸시·PR 생성을 **하지 마세요.** 봇(`PullRequestAgent`)이 전부 직접 합니다:

1. 봇이 `origin/main`에서 브랜치를 새로 따고 체크아웃해 둡니다 — 이미 올바른 브랜치 위에 있습니다
2. **여기서 파일을 고칩니다** ← 이 스킬의 일
3. 봇이 `git add --all` → 커밋 → 빌드 → 푸시 → `gh pr create`

그러니 `git` 명령으로 이력을 만들지 마세요. 커밋을 만들면 봇의 커밋과 겹쳐 브랜치가 어긋납니다.

작업 디렉터리는 운영 배포 소스가 아니라 봇 전용 클론입니다. 여기서 무엇을 고쳐도 서버에 바로 반영되지 않습니다.

## 반드시 남겨야 하는 것

**변경 사항이 하나도 없으면 실패로 처리됩니다.** 봇이 `git status --porcelain`으로 확인하고, 비어 있으면 "에이전트가 아무것도 고치지 않았다"로 끝냅니다. 계획대로 고칠 수 없다고 판단했다면 아무것도 안 하고 끝내지 말고, 무엇이 막았는지 설명하세요.

## 고치는 기준

- **계획에 있는 것만 고치세요.** 승인은 그 계획에 대한 승인입니다. 지나가다 보인 다른 문제는 고치지 말고 보고에 적습니다.
- **기존 코드 관례를 따르세요.** 주변 파일의 네이밍·레이어 구조·예외 처리·테스트 방식을 먼저 읽고 그대로 씁니다. 새 라이브러리나 새 패턴을 이 수정에서 도입하지 않습니다.
- **주석은 이유(WHY)만.** 코드만 봐도 아는 것은 쓰지 않습니다. TMT-BE의 기존 주석이 그 기준입니다.
- **테스트를 함께 고치거나 더하세요.** 동작이 바뀌면 그 동작을 덮는 테스트가 있어야 합니다. 기존 테스트가 깨지면 테스트를 지우는 게 아니라 수정이 맞는지 다시 봅니다.
- **빌드를 돌려 확인하세요.** 봇이 뒤에서 다시 돌리는데, 거기서 깨지면 PR이 아예 안 올라가고 사람이 다시 눌러야 합니다. 여기서 확인하면 고칠 기회가 있습니다.

## 계획이 틀렸다고 판단되면

계획은 분석 단계가 만든 것이라 틀릴 수 있습니다. 코드를 열어보니 원인이 다르면 **계획을 그대로 따르지 말고**, 실제 원인에 맞게 고친 뒤 무엇이 달랐는지 보고하세요. 사람이 승인한 것은 "이 증상을 고쳐달라"이지 "이 줄을 이렇게 바꿔달라"가 아닙니다.

다만 계획보다 **범위가 커지는 방향이면 고치지 마세요.** 그건 사람이 다시 판단할 몫입니다. 무엇이 필요한지만 적고 끝냅니다.

## 보고

작업 끝에 다음을 적습니다. 이 내용이 사람이 PR에서 읽을 유일한 설명입니다.

- 고친 파일과 각각 무엇을 왜 바꿨는지
- 계획과 달라진 부분이 있으면 그 이유
- 빌드 결과
- 고치지 않고 남긴 것 (지나가다 본 문제, 범위를 넘는다고 판단한 것)
